# Starfield completion acceptance

Primary verification: October 9, 2026. Updated on October 10 and 13, 2026. Iteration 14 canceled by the user. Giant formation chance remains native; strength does not increase it. This work closes the remaining release items after iteration 13.

## Changes

- Native seed can be planted in empty single AgriCraft crop sticks. Season, location, soil and both parts are verified by the original Starfield item. Canceled placement restores the seed, components, and empty crop sticks.
- Material is added to the real native plant, including the top and grown forage. One item per planting; Changing the material requires prior removal. Shift + empty hand removes material, saving UUID, genome and progress.
- One-time hand, scythe and automated collection leaves empty crop sticks of the previous material. For a regrowing crop, the material remains on the plant. Destruction and natural removal return the material once; Creative mode and canceled destruction do not create material. Carrying, rolling back and forming a giant do not provide additional returns.
- Client displays existing wood, iron and obsidian models around a real root. Sampling is limited by loaded chunks, block radius 64 and camera visibility; a separate index contains only plantings with material.
- A harvested coffee bean, when planted directly, reads both alleles from the product component. The schema, source species and item are validated; The native prohibition of coffee beans in the seed maker remains.
- Added English and Russian translations of the Starfield inspection settings in Jade; The translation check failure when opening the menu after disconnecting disappears.
- PneumaticCraft receives primary produce for the drone item filter. An empty native block loot table no longer interferes with harvesting. The filter does not harvest the plant and does not consume random numbers of the world.
- Without Starfield and with an unverified version, gameplay/tick/chunk integration callbacks, ItemStack.useOn interception, client render and cache events, magnifying glass inspection, and Jade providers are no longer registered. The result of the dependency metadata check is stored for the entire process. TOP performs native inspection only when integration is active. Network type declarations remain for protocol stability; The declarations themselves do not send plant data.

The graphical client without Starfield was separately tested after loading resources: there were no rendering/cache events, no magnifying glass inspection and ItemStack mixin (`no-starfield-client.log`, `no-starfield-client-result.txt` V `build/starfield-iteration0`).

This eliminates separate integration work on ticks/frames, interactions and loading chunks. Short checks of common APIs and type declarations at startup remain; No comparative FPS/TPS measurement was carried out. When a verified dependency is installed, the disabled setting retains the previous rules for storing dormant data - this mode differs from the physical absence of the mod.

## Clients and standalone installation

Two full graphical clients **StarfieldProbeA/B** went through eight stages on a real local dedicated server: initial full snapshots, change of material with the same UUID, transition to overworld, return, deletion of forage, traveling 1024 blocks away with actual chunk unload, return and new network connection of both players. The genome, UUID, seed template, material and shape are checked. Replay after changing the registration of handlers was performed on October 10 with Starfield: witness `build/starfield-iteration0/client-acceptance-result.txt`, server log `no-starfield-network-server.log`, client logs `no-starfield-network-A.log` / `no-starfield-network-B.log` in the same folder.

Fresh images of `neoforge/build/starfield-acceptance-client-A/screenshots/ProbeA-phase0.png` and `ProbeA-phase3.png`, as well as images of the second client, were checked: wooden, iron and obsidian models are located at native roots; after changing the material, the first root displays obsidian. The tall-crop and grown-forage models remain visible. Before confirming and taking a picture, the test waits for the compilation of the native section of the ground and twenty frames of the scene without a menu: an early picture with only crop sticks before the ground is ready is not considered visual confirmation. The camera, closing intro windows and hiding the HUD are done by test code only. The large farm in the graphic client and third-party shader packs were not measured by this launch.

This acceptance run found and fixed two bugs: the old cache after a long-distance teleport and the missing translation of the Jade setting when opening the menu after disconnecting. The client's `ClientLevel.hasChunk()` always returns true, so the actual loading is checked through `ClientChunkCache`; vanilla `drop()` does not publish unload for a chunk outside the new range. The server now explicitly sends cleanup on UnWatch.

In the rerun, the clients and server exited with code 0 and a successful Gradle result; the server saved all five dimensions. In the previous run, the save and main/server threads ended, but the development JVM was left with non-daemon worker pools waiting (`client-acceptance-server-exit-threads.txt`). Checking the bytecode of Architectury Transformer 5.2.91 shows that `ReadClasspathProviderImpl` creates a fixed thread pool and calls `awaitTermination(0, SECONDS)` without `shutdown()`. This is consistent with the dump and is different from the previous active loop `ChunkMap`. The test harness terminates the JVM only after ServerStopped and the server thread has completely terminated, like GameTestServer; it does not bypass stuck saves. This code is not included in the release. A regular installed release JAR will normally exit without such code.

The original Starfield reports errors in its collision models of chests and one window texture even when loading resources. These materials have not been modified here; they are not among the three tested crop sticks models.

The release artifact `AgriCraft-neoforge-1.21.1-4.0.19.jar` is installed in a separate regular NeoForge 21.1.226 server along with the original Starfield 0.6.3fix1 and Resourceful Config 3.0.11. There are no sources, test classes or probe mods on the classpath. Two consecutive processes loaded and saved the world normally and ended with code 0; the full base genotype and UUID of the real potato matched in SavedData after a restart. The check was repeated on the updated JAR after the handlers were disabled early. Witness: `build/starfield-standalone/result.txt`; logs `write.log` / `read.log` are nearby, startup - `build/starfield-iteration0/no-starfield-installed.log`. The check confirms the installation, saving, and normal exit of the release JAR, not the entire matrix of game actions in that individual installation.

SHA-256 of the verified updated release JAR: `c88f402b99910103675c72e7a4f195462238a8d216e08e6eb4a11f9a7aa1caaf`. Regular NeoForge and Fabric builds succeed (`no-starfield-build.log`); all six main, dev-shadow and sources archives are checked for the absence of test classes and Starfield resources (`no-starfield-archives.log`).

## Stopping the server

By user decision dated 10 October 2026, the previous non-reproducible freeze was excluded from the stable release blockers. The investigation for the current release has been completed; investigation resumes if it recurs. Logs and test diagnostics are saved; a fix for an unknown cause is not announced.

Previously, the combined migration-write + reload completed seven checks, but got stuck at stop. The dump shows the re-execution of `ChunkMap.scheduleUnload` inside `processUnloads`, not the genetic or AgriCraft daily cycle. The individual migration and the current full profile are saved as usual. Repeating the same combined write + reload passed **7/7** with the usual JVM save and exit (`acceptance-migration-reload-write.log`); the subsequent disabled/read processes each passed **2/2** and confirmed persisted data from disk. The cause of the original single incident has not been determined; repetition is not evidence of correction of its cause.

Additional investigation 10 October: ten GameTest processes with generation/unloading monitoring completed normally. The exact original coordinates and a set of seven tests were restored, write/disabled/read were repeated, a copy of the existing migration world was checked. In the last run, monitoring is enabled at the entry to stopServer, before other mods' shutdown handlers. There were no unready holders or generation requests registered after the start of monitoring. Detailed evidence, replication and limits - in [hang investigation](SAVE-HANG-INVESTIGATION.md). The root cause of the previous incident is still unknown.

Additionally, a regular installed release JAR in two independent JVMs successfully executed a real `/reload`, removing the forced chunk-loading ticket, and a regular `stop` while saving five dimensions. The full genotype and UUID matched after a restart (`save-investigation-installed.log`, `build/starfield-standalone/reload-result.txt`). Builds and verification of the current six archives are successful; SHA-256 release has not changed. This is an additional stop check, not a fix for the unknown cause of an old crash.

In [NeoForge #1403](https://github.com/neoforged/NeoForge/issues/1403), the author of a similar case established a call to the unloaded position through `getBlockEntity`, causing generation during unloading, and closed the issue. This is not a confirmed NeoForge bug and not proof that we have the same initiator. No change to Minecraft or Starfield adds a bypass, force save, or skip unloading.
