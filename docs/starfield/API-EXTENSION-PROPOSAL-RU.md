# Предложение узких расширений Starfield API

Черновик для обсуждения; не отправлен автору и не меняет Starfield.
Основание: официальный `0.6.3fix1`, commit `df2151c66a2a9c02855e4db23108e57c422ce78e`.

После проверки нативного блока с отдельным SavedData выбран этот способ представления.
Предложения 1–2 ниже относятся к отвергнутой схеме с чужим блоком и теперь не блокируют
продолжение интеграции. Предложение 3 всё ещё относится к будущему семенному аппарату.

## 1. Общий исполнитель нативного вида

Задача: представить растение Starfield на чужом блоке и сохранить его точные правила без
второй реализации фаз/удобрений/особенностей видов. Имеющийся `StardewCropRuntimeAdapter`
предоставляет планировщик и контекст, но требует самостоятельной мутации растения аддоном.

Нужна публичная операция расчёта одного дня нативного вида по снимку его состояния и
`StardewCropDailyContext`, с интерфейсом чтения/записи представления. Нативный блок должен
использовать тот же исполнитель. Реализация принадлежит Starfield и сохраняет dispatch
особенностей rice, taro, fiber, wild seeds и других видов.

Контракт должен явно определить:

- источник метаданных вида и авторитетного снимка состояния;
- пригодность почвы, реальную воду и уже применённый допуск неплодородной почвы;
- исторический сезон/дату и исключения места, без чтения нынешнего глобального сезона;
- переход фаз, повторный рост, смерть/замену и действия над дополнительными частями;
- единственное применение нативного удобрения и поправки генов к срокам;
- кто сохраняет дату и предотвращает повтор того же дня;
- commit результата после повторной проверки идентичности посадки.

Доступ к приватному методу через reflection/access transformer, временная подмена блока или
измерения не удовлетворяет этому контракту. Упрощённый исполнитель только `phaseDays` также
не сохранит все нативные особенности.

Общий расчёт урожая нужен по аналогичной схеме: нативный вид + снимок + существующий
`StardewCropHarvestContext` → подготовленные стеки, опыт и переход состояния. Ошибка до
commit не должна выдавать продукцию. Звёздность, дополнительные дропы и обязательные
инструменты остаются правилами Starfield.

## 2. Безопасная замена зарегистрированных растений с block entity гигантом

`GiantCropGrowth` сейчас отклоняет любую ячейку с block entity. Это защищает контейнеры,
но также исключает зарегистрированное растение на жердочках AgriCraft.

Нужен opt-in контракт только для распознанной корневой посадки: подготовка полного снимка,
разрешение удаления, commit и восстановление при неуспехе всей операции. Произвольные
контейнеры продолжают отклоняться. Возврат материала жердочек/очистка данных выполняются
один раз после успеха полного участка, а не при удалении каждой части.

Поправка к исходному плану по зрелости: официальный API требует зрелости и воды ведущего
растения; остальные корни должны быть целыми, того же продукта и в допустимом участке.
Сборка имеет пять гигантских продуктов: cauliflower, melon, pumpkin, powder_melon, qi_fruit,
базовый шанс 1%, участок 3×3. Не следует добавлять требование зрелости всех девяти, если целью
остаётся равенство нативной грядке.

## 3. Перенос компонентов в семенном аппарате

`StardewArtisanResolvers.SeedMakerOutputResolver` получает `Item` и выбирает выходной `Item`.
`SeedMakerBlockEntity` после нативных бросков создаёт новый `ItemStack`. Геном входного
предмета невозможно передать через такой resolver.

Нужен обработчик результата по защитной копии входного стека и окончательно выбранного
выходного стека, после нативного определения вида/количества, до сохранения производственного
плана. Обработчик переносит только свои компоненты и не меняет нативный бросок.
Несовпадающий вид, mixed seeds или бонусное древнее семя не получают чужой геном.
В частности, нативный grape разрешается в summer wild seeds — это не возврат grape seeds.

## Альтернативное представление

В прототипе сохранён настоящий нативный блок, жердочки/геном хранятся в отдельном состоянии мира.
Тогда потребуется расширить собственный AgriCraft: lookup `AgriCrop` для внешнего корня,
визуальное отображение жердочек, селекция и взаимодействие инструментов.
Проверены четыре нативных цикла, повторный рост и сборка настоящего гиганта. Это выбранная
архитектура для следующих итераций; lookup, отображение и игровые инструменты ещё не реализованы.
Подробности и пределы доказательства — в [спецификации итерации 0](ITERATION-0-SPEC-RU.md).
